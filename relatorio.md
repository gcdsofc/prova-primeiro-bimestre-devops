 Questao 1 — A Jornada Completa (Aulas 01 a 07)

Durante o projeto, eu conectei as aulas do bimestre seguindo uma ordem parecida com a construcao real de uma aplicacao DevOps. Primeiro comecei pelo Git, criando o repositorio, organizando a estrutura inicial, usando commits convencionais e separando a infraestrutura em uma feature branch. Depois desenvolvi a API de Reservas em Node.js/Express, começando com uma rota simples de health check e evoluindo para o CRUD completo. Em seguida, integrei a API ao PostgreSQL para que as reservas fossem persistidas em banco de dados, e nao apenas em memoria. Depois containerizei a aplicacao com Docker, criando o Dockerfile e registrando evidencia do build e da execucao. Na etapa seguinte usei Docker Compose para subir a API e o PostgreSQL juntos, com rede customizada, volume nomeado, healthcheck e depends_on com condicao. Depois avancei para Terraform, criando modulos separados para VPC, Security Groups, EC2 e RDS. Tambem configurei o estado remoto com S3 e DynamoDB, respeitando as restricoes do AWS Academy Learner Lab. Por fim, validei a aplicacao na nuvem, testando a EC2 publica acessando o RDS privado e executando as rotas da API. Cada aula apareceu como uma camada do projeto: Git para versionamento, Docker para empacotamento, Compose para ambiente local, Terraform para infraestrutura, modulos para organizacao, AWS para execucao real e IA para apoio no processo.

Questao 3 — Infraestrutura, Segurança e Learner Lab

A arquitetura AWS foi criada no AWS Academy Learner Lab, na regiao us-east-1. A infraestrutura foi feita com Terraform modularizado, separando VPC, Security Groups, EC2 e RDS. A VPC possui sub-redes publicas e privadas em duas zonas de disponibilidade. A EC2 ficou em uma subnet publica porque a API precisa ser acessada pela internet na porta 3000. Ja o RDS PostgreSQL ficou em subnets privadas, com publicly_accessible = false, porque o banco de dados nao deve receber acesso direto da internet. A comunicacao com o RDS foi controlada pelo Security Group: a porta 5432 foi liberada apenas a partir do Security Group da EC2. A EC2 teve acesso publico na porta 3000 para a API e acesso SSH limitado, seguindo a ideia de menor privilegio. O RDS tambem foi configurado com storage_encrypted = true. No Learner Lab nao foi permitido criar usuarios, grupos ou roles IAM proprios, entao foi usado o que o ambiente ja fornece, como LabRole e LabInstanceProfile. As credenciais usadas foram temporarias, copiadas do AWS Details com Session Token. Uma limitacao encontrada foi o bloqueio de algumas permissoes pelo proprio laboratorio, como a leitura de Object Lock no S3. Por isso, parte do backend remoto precisou ser criada respeitando as permissoes disponiveis no ambiente. Ao final, executei terraform destroy para evitar consumo de creditos.

Questao 4 — Validação e Responsabilidade

Antes de rodar terraform apply, apliquei uma sequencia de validacoes para reduzir risco. Primeiro organizei o codigo e rodei terraform fmt para padronizar os arquivos. Depois rodei terraform validate para verificar se a sintaxe e a composicao dos modulos estavam corretas. Em seguida gerei o terraform plan e conferi se apareciam os recursos esperados: VPC, subnets publicas e privadas, Security Groups, EC2, RDS, subnet group, RDS privado e storage encrypted. Tambem conferi que o RDS estava com publicly_accessible = false e que o banco ficava nas subnets privadas. Durante a execucao, quando apareceram erros, nao simplesmente ignorei. Ajustei a senha do RDS por causa das regras da AWS, gerei um novo plano quando o state mudou e diagnostiquei a API na EC2 usando SSM. Quando a API nao respondeu na porta 3000, investiguei logs e descobri que o RDS exigia conexao SSL. Depois corrigi a conexao, validei /health e /db-health, e testei o CRUD completo gravando no PostgreSQL da nuvem. Se eu aceitasse codigo de IA sem revisar, poderia deixar banco publico, security group aberto demais, senha em arquivo versionado, infraestrutura consumindo credito ou aplicacao sem persistencia real. A evolucao Git, Docker, Compose, Terraform e modulos me preparou para usar IA de forma melhor, porque eu passei a entender o que precisava validar em cada camada. No final, a responsabilidade foi minha: testar, salvar evidencias, corrigir erros e destruir os recursos depois.
